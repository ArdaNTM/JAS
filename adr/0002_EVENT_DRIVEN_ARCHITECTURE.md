# 1. Context

JARVIS consists of many independent runtime components.

Examples include:

- Voice System
- Vision System
- Browser
- Memory
- Planner
- Coding Agent
- Research Agent
- MCP Layer
- Plugin System
- Future Extensions

These components must cooperate without becoming tightly coupled.

The architecture must support:

- parallel execution
- asynchronous execution
- future distributed execution
- subsystem replacement
- observability
- fault isolation

Traditional synchronous communication is insufficient for long-term scalability.

---

# 2. Decision

JARVIS SHALL adopt an Event-Driven Architecture (EDA).

Every meaningful state change inside the system SHALL generate one or more events.

Events SHALL become the primary communication mechanism between runtime components.

Direct communication SHALL only be used when explicitly required by performance or correctness.

---

# 3. Motivation

Event-driven systems provide:

- loose coupling
- extensibility
- scalability
- easier debugging
- improved observability
- simpler plugin integration
- easier future distribution

These properties closely align with the long-term vision of JARVIS.

---

# 4. Event Definition

An Event represents a completed fact.

Events describe something that has already happened.

Examples:

UserSpeechCaptured

IntentRecognized

TaskCreated

TaskCompleted

MemoryStored

BrowserOpened

PluginLoaded

VisionObjectDetected

CodingFinished

ResearchCompleted

ModelLoaded

ShutdownRequested

---

# 5. Event Rules

Every event SHALL:

- have a unique identifier
- contain a timestamp
- have an event type
- include its source subsystem
- contain structured payload data
- remain immutable after publication

Events SHALL NOT be modified after creation.

---

# 6. Event Lifecycle

The standard lifecycle is:

1. Event Created
2. Event Published
3. Event Routed
4. Event Processed
5. Event Logged
6. Event Archived (optional)

---

# 7. Event Ownership

Only the subsystem that owns an operation may publish the corresponding event.

Example:

Voice System

↓

publishes

↓

VoiceCaptured

The Planner SHALL NOT publish VoiceCaptured events.

---

# 8. Event Consumers

Any subsystem may subscribe to events through the Kernel.

The publisher SHALL NOT know which components consume an event.

This guarantees loose coupling.

---

# 9. Event Categories

The architecture defines the following categories:

System Events

User Events

Memory Events

Planning Events

Tool Events

Agent Events

Plugin Events

MCP Events

Security Events

Lifecycle Events

Diagnostic Events

Future versions may introduce additional categories.

---

# 10. Ordering

Events generated by a single subsystem SHALL preserve publication order.

Global ordering across all subsystems is not required.

Consumers SHALL NOT depend on global ordering.

---

# 11. Reliability

Event delivery SHALL support:

- retry
- timeout
- failure reporting
- dead-letter handling (future)
- duplicate detection (future)

No event shall silently disappear.

---

# 12. Logging

Every published event SHALL be observable.

Logging shall include:

Event ID

Timestamp

Publisher

Consumers

Processing Duration

Result

Sensitive payload data SHALL NOT be logged unless explicitly allowed.

---

# 13. Security

Events SHALL NOT bypass the Permission Engine.

Security-sensitive events require authorization before processing.

Unauthorized subscribers SHALL NOT receive protected events.

---

# 14. Alternatives Considered

Alternative A

Direct Function Calls

Rejected.

Reason:

High coupling.

Poor extensibility.

---

Alternative B

Shared Global State

Rejected.

Reason:

Hidden dependencies.

Synchronization complexity.

Hard debugging.

---

Alternative C

Message Broker Only

Rejected for Version 1.x.

Reason:

Adds unnecessary infrastructure for local-first architecture.

May become appropriate in future distributed deployments.

---

# 15. Consequences

Positive:

Excellent modularity.

Simpler plugin development.

Improved scalability.

Better observability.

Future distributed support.

Cleaner subsystem boundaries.

Negative:

Additional implementation complexity.

Slight runtime overhead.

More infrastructure inside the Kernel.

These trade-offs are considered acceptable.

---

# 16. Future Evolution

Future versions may support:

Event persistence.

Remote event routing.

Distributed event buses.

Event replay.

Streaming analytics.

Cross-device synchronization.

The architectural principles defined in this ADR SHALL remain valid.

---

# 17. Compliance Requirements

Every subsystem SHALL:

Publish lifecycle events.

Consume events only through approved interfaces.

Avoid direct subsystem dependencies whenever events are appropriate.

Document every event type it publishes.
